# Testing Approach

## Why This Combination?

This project is a Spring Boot microservices system where correctness depends on four distinct integration surfaces:
- PostgreSQL (two separate databases)
- Amazon S3 (LocalStack in dev)
- RabbitMQ (async message passing between services)
- HTTP between services (resource-processor calls both resource-service and song-service)

A single testing strategy cannot adequately cover all of these. The chosen approach combines five test types across three different frameworks, each addressing a different failure mode and audience.

---

## The Chosen Distribution

| Type | Share | Framework | Primary risk addressed |
|---|---|---|---|
| Unit tests | 40% | JUnit 5 + Mockito | Logic bugs in service/domain classes |
| Integration tests | 25% | Spock (Groovy) | Misconfigured adapters (wrong SQL, wrong queue name, wrong S3 key) |
| Component tests | 20% | Cucumber (Gherkin) | Business-level behaviour regressions within a single service |
| Contract tests | 10% | Pact JVM | Schema drift between independently deployed services |
| E2E tests | 5% | Cucumber (Gherkin) | Flow-level regressions across the full async pipeline |

This is **not** a 100% unit-test strategy. The project's complexity lives in its infrastructure integrations, so the test weight shifts toward integration and component tests compared to a typical monolith.

---

## Framework Choices and Why

### Unit tests – JUnit 5

JUnit 5 is the standard for Java unit tests. It integrates natively with Spring Boot Test, Mockito, and JaCoCo. For `resource-service` — the selected module — there are no Groovy-friendly concerns and the test scenarios are straightforward assertions about method return values and mock invocations. JUnit 5 + Mockito covers this with minimal boilerplate.

**Why resource-service as the selected module?** It is the most logic-dense service in the system: it owns the upload validation, S3 key generation, delete orchestration, and RabbitMQ event publishing. All of its collaborators are injectable interfaces, making them trivially mockable. It is also the entry point of the upload flow, so bugs there affect every downstream service.

### Integration tests – Spock

Spock's Groovy DSL is chosen for integration tests because integration scenarios are inherently multi-step stories: "given a database with two rows, when one is deleted, then only the other remains." The `given/when/then` blocks are structural in Spock (not just comments), and `@Unroll` with data tables eliminates repeated boilerplate for multi-case adapter tests. Spock runs on JUnit 5's platform so it integrates with the same Maven Surefire/Failsafe configuration and JaCoCo setup as the rest of the project.

### Component and E2E tests – Cucumber

Cucumber is chosen for both component and E2E tests because business-level and end-to-end scenarios need to be readable by non-engineers (product owners, QA leads, technical writers). Gherkin feature files act as living documentation: they describe what the system does in plain language and fail if the implementation drifts. Using the same framework for both layers also means step definitions can be shared between component and E2E tests, reducing duplication.

The key difference between the two layers is scope:
- **Component tests** start one service (full Spring context) with its dependencies containerised and downstream services stubbed by WireMock.
- **E2E tests** start all five services via `compose-e2e.yaml` and speak only to the gateway, never directly to inner services.

### Contract tests – Pact JVM

Pact is chosen because it supports both communication styles used in this project — synchronous HTTP and asynchronous messaging — under a single framework. The Pact Broker creates a version-tracked audit trail of every inter-service contract. It also enables **stub propagation**: the pact file generated by the consumer tests can be replayed by `pact-jvm-server` or imported into WireMock, meaning component and E2E tests can pull stubs from the broker instead of maintaining separate hand-written WireMock mappings. This creates a single source of truth: the contract defines both what is verified and what is stubbed.

---

## Why Not 100% Unit Tests?

Unit tests are fast and precise but cannot catch a wrong RabbitMQ routing key, a missing database column, or a misconfigured S3 bucket policy. In this project, those integration seams are where the majority of real bugs surface. Mocking them away at the unit level gives false confidence and shifts the failure discovery from CI to production.

---

## Why Not 100% E2E Tests?

E2E tests are slow (~10 minutes per run), brittle due to async timing (Awaitility timeouts), and give a low-resolution failure signal (the flow broke, but where?). Running them on every commit would slow the feedback loop to the point where developers stop waiting for CI results. They are reserved for validating merge-to-main candidates only.

---

## How the Layers Complement Each Other

### Unit + Integration = fast, precise inner loop

Unit tests run in milliseconds and catch logic mistakes early. Spock integration tests catch the SQL and schema mistakes that unit tests miss, in a format that clearly narrates what the adapter is supposed to do. Together they complete in under 4 minutes and run on every commit.

### Component tests = service-level business confidence

A Cucumber component test boots the full Spring context with real containers but stubs downstream HTTP services with WireMock stubs sourced from the Pact Broker. This catches wiring bugs — missing `@Bean`, wrong property binding, incorrect Jackson serialization — that unit tests miss entirely because Mockito bypasses the Spring container. Scenarios are written at the business level ("When I upload a valid MP3 file"), not at the technical level ("when repository.save() is called"), so they remain valid across refactors.

### Contract tests = safe independent deployment

In a microservices system, services are deployed independently. Without contract tests, a breaking change to `POST /songs` in song-service can go undetected until resource-processor crashes in production. Pact consumer-driven contracts create an automated safety net: the consumer defines what it expects, the provider is verified against those expectations in CI, and the Pact Broker blocks the provider deployment if verification fails. Covering both HTTP and messaging contracts means there are no unguarded integration surfaces.

### E2E tests = release gate

E2E tests are the only tests that exercise Eureka service discovery and gateway routing together. They validate the complete async upload flow — from `POST /resources` through RabbitMQ to song-service — in a way that no lower-level test can. Because they are slow and infrastructure-heavy, they run once per merge to `main` rather than on every commit. They act as a final safety net, not the primary feedback mechanism.

---

## Stability vs. Coverage Trade-off

| Layer | Stability | Coverage signal |
|---|---|---|
| Unit (JUnit 5) | Very high – no containers, no I/O | Service logic correctness |
| Integration (Spock) | High – isolated containers per spec | Adapter configuration |
| Component (Cucumber) | Medium – full context, WireMock stubs | Business behaviour per service |
| Contract (Pact) | High – no runtime needed for consumer | API and message schema |
| E2E (Cucumber) | Lower – async timing, multi-container | End-to-end flow correctness |

The pyramid shape is deliberate: stable fast tests form the base; slow and environment-sensitive tests are kept minimal. This keeps the CI pipeline below 10 minutes on a PR and below 20 minutes on a merge-to-main.

---

## Coverage Targets

- **Unit (JUnit 5):** 80%+ line coverage on `resource-service` service and domain classes, enforced by a JaCoCo `<minimum>` rule in Maven.
- **Integration (Spock):** All repository methods and all external-adapter classes (S3, RabbitMQ producer/consumer) covered by at least one specification.
- **Component (Cucumber):** 100% of public API endpoints and all RabbitMQ listener paths covered by at least one scenario per service.
- **Contract (Pact):** 100% of cross-service HTTP endpoints and all messaging interfaces covered by at least one Pact interaction.
- **E2E (Cucumber):** All six user-visible scenarios (upload, download, delete, async metadata extraction, 400 on invalid input, 404 on missing resource) run as the merge gate.
